# 入門コース 提出課題の設計と提出方法（計画書）

- 作成: Claude（2026-09-27）
- 対象: 入門コース 14 本（`courses/intro.html`）
- 依頼: 各トピックの課題の設定と提出方法を決める。提出物は「実験に使ったパラメータ付き URL」と「考察」
- 状態: **課題文確定**（§9.6 で §10.2 の修正案を採用。2026-09-28）。提出票は入っている

---

## 0. 要旨

1. 演習カード（予想 → 操作 → 確認。答えは「期待される観察」で見られる）とは別に、**答えが 1 つに決まらない探究課題**を各トピックに 1 本置く。学生は条件を自分で探し、その条件を **URL で提出**して、なぜそうなるかを考察する
2. 提出物は、どのトピックも同じ型にする: **URL（原則 2 本: 比べる A と B）＋ 観察（数値）＋ 考察**。先生は URL を開けば、学生と同じ条件を再現して確かめられる
3. 提出方法は、各トピックのページに**「提出票」**を置き、そこで URL・観察・考察をまとめたテキストを作ってコピーし、LMS（大学の授業支援システム）に貼る。サイトはサーバーを持たないので、ページの外には何も送らない
4. URL で再現できないところが 3 つあった（alpha-beta は URL 非対応、gfx-ui-canvas はドラッグ位置が URL に入らない、手で操作する 3 本は結果が URL に入らない）。前の 2 つは 2026-09-27 に実装で直した。手で操作する 3 本は結果の記録を添えてもらう

## 1. 方針

### 1.1 演習カードとの違い

| | 演習カード（既存） | 提出課題（今回） |
|---|---|---|
| 目的 | 要点の現象を一度見る | 条件を自分で探し、仕組みで説明する |
| 条件 | URL で指定済み | 学生が決める（一部は個人ごとに指定） |
| 答え | 「期待される観察」で見られる | ページには載せない（教員用の想定だけ本書に書く） |
| 提出 | しない | URL と考察を提出する |

課題は演習カードのあとに取り組む前提で書く。演習カードで見た現象を、条件を変えて確かめ直す形にする。

### 1.2 提出物の型（全トピック共通）

1. **URL**: 原則 2 本（A: 現象が起きない／起きる前、B: 起きる／起きた後）。比べることで考察が書ける。1 本や 3 本の課題もある
2. **観察**: その URL で見た数値（結果表・状態表示・ログの値）。どの数値を書くかは課題ごとに指定する
3. **考察**: 次の 2 点を含める。目安 **100〜200 字**（§8 決定 4）
   - 事実: A と B で何が違ったか（数値で）
   - 説明: なぜそうなるか（仕組み・式。点線の用語を使ってよい）

### 1.3 評価の目安（2 観点。§8 決定 4）

| 観点 | 見るところ |
|---|---|
| 再現性 | URL を開くと課題の条件（個人条件を含む）どおりで、書かれた数値が出る。観察の数値がそろっていて正しい |
| 考察 | A と B の違いを数値で書き、仕組みで説明している |

点数の配分は先生が決める。

### 1.4 個人ごとの条件（任意。§7 Q3）

同じ答えを写しにくくするため、いくつかの課題では**学籍番号の末尾 1 桁 d（0〜9）**で数値を変える。例: 人工遅延 L = 10 + 5d ms。提出票に d を入れると、その人の条件が表示される。個人条件が無い課題は、答えが 1 つに決まらない作りにしてある。

## 2. 提出方法

### 2.1 推奨: サイト内の「提出票」→ LMS に貼る

各トピックのページ（`?course=intro` で開いたとき）の演習カードの下に「提出課題」の節を置く。

1. 課題文を表示する（`js/courses/intro-assignments.js` を正本にする。演習カードと同じ仕組み）
2. 学籍番号の末尾 d を入れると、個人条件が表示される（個人条件がある課題だけ）
3. 「今の設定を URL A にする」「URL B にする」ボタン。今のパラメータ付き URL（`この設定のURLをコピー` と同じもの）を枠に入れる
4. 観察・考察を書く欄。書いた内容はそのブラウザにだけ下書き保存（localStorage）する
5. 「提出用テキストをコピー」で、次のようなテキストを作ってクリップボードに入れる。学生はこれを LMS の提出欄に貼る

```
【入門コース 提出課題 1: game-loop — 打ち切らない MAX_STEPS を予想する】
個人条件: d=3 → 人工遅延 25 ms
URL A: https://kobashi.github.io/game-algo-lab/algorithms/game-loop.html?course=intro&mode=fixed&lag=25&maxsteps=2
URL B: https://kobashi.github.io/game-algo-lab/algorithms/game-loop.html?course=intro&mode=fixed&lag=25&maxsteps=1
観察: …
考察: …
```

- サイトはサーバーを持たないので、ページの外には何も送らない。氏名も入れない（LMS 側で分かる）
- URL の枠は、そのトピックのページの URL しか受け付けない（別トピックの URL の取り違えを防ぐ）
- 既定値のままの URL（パラメータが付かない）は「条件を変えていません」と注意を出す

### 2.2 代替: Google フォーム

LMS が使いにくい場合は、トピックごとに Google フォーム（URL A・URL B・観察・考察の 4 欄）を作り、提出票から「フォームを開く」リンクで飛ぶ。回答がスプレッドシートに集まるので採点しやすい。フォームは先生のアカウントで作るので、Claude からは作れない。

### 2.3 教員用: 提出 URL の確認ページ（後回し可）

LMS から集めた提出テキストを貼ると、URL を取り出して一覧にするページ（`courses/check.html`）。

- トピックの取り違え
- 範囲外の値
- 既定値のまま
- 個人条件と合わない値

を目印付きで示し、リンクから 1 つずつ開いて確かめる。採点は先生がする。

## 3. URL の再現性の点検（2026-09-27）

各トピックの URL パラメータ（`この設定のURLをコピー` で付くもの）と、課題に要る条件を照らし合わせた。

| トピック | URL で指定できるもの | 課題に要るもの | 判定 |
|---|---|---|---|
| game-loop | mode, dt, lag, spike, maxsteps, speed, balls, compare, ref など | 遅延・MAX_STEPS・モード | ○ |
| input-basics | longms, speed | 閾値。結果はキー操作なので URL に入らない | △ ログを添える |
| velocity-motion | vx, vy, dt, obs, thick など | 速度・dt・厚み | ○ |
| accel-gravity | g, vx, rest など | 重力・反発 | ○ |
| circle-collision | 円と箱の位置・大きさ | 配置 | ○ |
| coyote-time | coyote, ms, speed | 猶予。成否は手操作なので URL に入らない | △ 統計を添える |
| gfx-camera | follow, dead, speed | 係数・デッドゾーン。遅れは右に歩けば再現できる | ○ |
| gfx-ui-canvas | res, vieww, anchor, px, py（Pivot）, **ox, oy（Offset）** | Offset（ドラッグ位置） | ○（2026-09-27 に `ox`・`oy` と数値入力欄を追加） |
| sfx-events | ev, freq, dur, gain | 1 つのイベントの音 | ○（イベントごとに 1 本） |
| fsm | initial, from, ev, to, script | 遷移の上書き・イベント列 | ○ |
| rng-seed | algo, seed, n, a, c, m など | LCG の a・c・m | ○ |
| minimax | leaves, depth, eval | 葉の値 | ○ |
| alpha-beta | **leaves, speed** | 葉の並び | ○（2026-09-27 に葉の入力欄・`leaves`・URL コピーを追加） |
| tic-tac-toe | preset, ab, memo, sym, mcn, mcseed | プリセット局面・試行回数・シード | ○（自作の局面は入らない。今回の課題では使わない） |

ついでに見つけたこと: velocity-motion のすり抜けの表示は「|v|·dt が厚み 8px を超えた」だったが、判定にはボールの直径（24 px）と位置の巡り合わせも関わる（`circleAabbTunneled`）。2026-09-27 に「前後どちらの位置でも障害物に重ならなかった（厚み 8px ＋ ボールの直径 24px = 32px）」に直した（§6 I5）。課題 3 の考察の題材にもなる。

## 4. 課題（14 本）

書式: **問い** / 個人条件 / 提出する URL / 観察に書くこと / 考察の観点 / 教員の確認（想定の答え）。想定の答えは、実装のあとに Claude がブラウザで確かめて確定する（「要確認」と書いたもの）。

### 段1 まず動かす

#### 課題 1. game-loop — 打ち切らない MAX_STEPS を予想する

- **問い**: 重いフレームが続くとき、1 フレームに何回更新すれば遅れずに済むか。
- **個人条件**: 人工遅延 L = 80 − 5d ms（固定 timestep、毎フレーム。§11 で変更）
- **URL**: A = 打ち切りが出ない最小の MAX_STEPS、B = それより 1 小さい MAX_STEPS。どちらも `mode=fixed&lag=L&maxsteps=…`
- **観察**: 平均 updates/フレーム、打ち切りの回数、3 秒分にかかった時間（B）
- **考察**: なぜその回数か（1 フレームの実経過 16.7 + L ms とアキュムレータで説明）。B でシミュレーションが遅れる理由。打ち切りが無ければ何が起きるか（スパイラル・オブ・デス）
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

#### 課題 2. input-basics — チャージ攻撃の閾値を決める

- **問い**: 溜め攻撃の「長押し」の閾値は何 ms がよいか。
- **個人条件**: なし（閾値は自分で決める）
- **URL**: A・B = 閾値を 2 通りにした `input-basics.html?longms=…`
- **観察**: イベントログの行（Charge が出たとき・出なかったとき）。押していた長さ
- **考察**: Jump・Fire・Charge がそれぞれ held・down・up のどれを使っているか。閾値が短すぎる／長すぎるとプレイヤーはどう感じるか。判定がフレーム単位（約 16.7 ms 刻み）になる影響
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

### 段2 物を動かす

#### 課題 3. velocity-motion — すり抜けの境目を探す

- **問い**: 障害物の厚みに対して、1 歩をどこまで大きくすると、すり抜けるか。
- **個人条件**: 横の速さ vx = 195 + 5d、障害物の厚み 10 px。`vy=0&obs=1&trail=1`（§11 で変更）
- **URL**: A = すり抜けない最大の dt、B = すり抜ける最小の dt
- **観察**: A・B の |v|·dt、B で何ステップ目にすり抜けたか
- **考察**: 境目が厚み T とずれる理由（ボールの大きさ、当たり判定を「その瞬間の位置」でしか調べないこと）。すり抜けを防ぐ方法
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

#### 課題 4. accel-gravity — 狙った高さの比を作る

- **問い**: 跳ねるたびに高さが決まった割合になるよう、反発係数を選べるか。
- **個人条件**: 目標の高さの比 R = (0.9 − 0.05d)²（§11 で変更）
- **URL**: A = 予想した反発係数、B = A と同じ反発係数で重力 g を変えたもの
- **観察**: 最高点の列（A → B → C …）と隣どうしの比
- **考察**: 比が反発係数の 2 乗になる理由。g を変えても比が変わらない理由。ずれがあればその理由（刻みの粗さ）
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

#### 課題 5. circle-collision — 角でぎりぎり触れる配置

- **問い**: 円が箱の角に触れる瞬間を作れるか。辺で触れるときと何が違うか。
- **個人条件**: 円 A の半径 = 30 + 3d（§11 で変更）
- **URL**: A = 円 A が箱の角に接触（HIT）、B = そこから 1 px 離して miss
- **観察**: 円 A–AABB の距離 d と判定、最近点が角に来ていること
- **考察**: Clamp で最近点が角になる理由。辺で触れるときとの違い。平方根を使わずに比べる方法
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

### 段3 手ざわりを作る

#### 課題 6. coyote-time — 猶予の長さを決める

- **問い**: 自分のゲームに採用するなら、猶予は何 ms がよいか。
- **個人条件**: なし
- **URL**: 3 本 = 猶予 0 ms と、自分で選んだ 2 つの長さ（`coyote=…&ms=…`）
- **観察**: それぞれ崖から落ちながら 10 回試した成功・失敗の数（統計表の値。R キーで足場に戻る）
- **考察**: 成功率の変わり方。猶予が長すぎると何が不自然になるか。採用する値と理由
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

#### 課題 7. gfx-camera — ジャンルに合うカメラ

- **問い**: 素早いアクションと、ゆったりした探索で、カメラの設定をどう変えるか。
- **個人条件**: なし
- **URL**: A = アクション向け、B = 探索向け（`follow=…&dead=…`）
- **観察**: 右に歩き続けたときに遅れが落ち着いた値（px）
- **考察**: 追従係数と遅れの関係（1 歩の移動量と係数から遅れを予想し、実測と比べる）。デッドゾーンの役割
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

### 段4 見せる・鳴らす

#### 課題 8. gfx-ui-canvas — どの幅でも崩れない HUD

- **問い**: 画面の幅が変わっても、決めた場所に UI を置き続けられるか。
- **個人条件**: 置く場所 = d + 2 を 5 で割った余りで決める（0 左上、1 右上、2 中央、3 右下、4 下中央）。端から 16 px の余白（§11 で変更）
- **URL**: 3 本 = 幅 480・640・960 で、Anchor・Pivot・Offset（`ox`・`oy`）は同じ
- **観察**: 3 つの幅でのボタン左上の座標、端からの距離
- **考察**: Anchor と Pivot をどう選んだか、その理由。左上 Anchor のままだとどうなるか
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

#### 課題 9. sfx-events — 音で出来事を区別する

- **問い**: Hit と Pickup を、音だけで聞き分けられるようにできるか。
- **個人条件**: なし
- **URL**: A = Hit の音、B = Pickup の音（`ev=…&freq=…&dur=…&gain=…`）
- **観察**: ログの周波数・長さ。ミュートにしたときのログ
- **考察**: 音を変えるのに、イベントを出す側を変えなくてよい理由。購読者をもう 1 つ足すなら何に使うか
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

### 段5 状態と乱数

#### 課題 10. fsm — 遷移 1 本で新しい振る舞いを作る

- **問い**: 遷移表の 1 マスだけを変えて、キャラに新しい振る舞いをさせられるか。
- **個人条件**: なし
- **URL**: A = 変更前、B = 遷移を 1 本上書きし、その違いが出るイベント列を `script` に入れたもの
- **観察**: 状態履歴（A と B で分かれるところ）。到達できない状態（灰色）の変化
- **考察**: 表の 1 マスで振る舞いが変わる理由。変更で新しく困ること（抜け出せない状態や、届かなくなる状態）
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

#### 課題 11. rng-seed — 周期が最大になる LCG

- **問い**: 法 m の LCG で、周期がちょうど m になる a・c の組はどんな組か。
- **個人条件**: m = 2^(6 + (d + 1) を 4 で割った余り)（64〜512。§11 で変更）
- **URL**: A = 周期が m になる a・c、B = 周期が m より短くなる a・c
- **観察**: 周期の表示、ヒストグラムの様子
- **考察**: 周期が m を超えない理由。周期が m になる組に共通すること（予想で良い）。周期が短いと何が困るか
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

### 段6 考えるAI

#### 課題 12. minimax — 最善手を変える最小の変更

- **問い**: 葉を 1 つだけ変えて最善手を変えるには、どの葉をどれだけ変えればよいか。
- **個人条件**: なし（既定の葉から始める）
- **URL**: A = 最善手が変わらない最大の変更、B = 変わる最小の変更（`leaves=…`）
- **観察**: 根の値と最善手
- **考察**: どの葉が答えを決めているか。その葉を変えても答えが変わらない範囲がある理由（MIN が別の葉を選ぶ）
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

#### 課題 13. alpha-beta — 刈りの多い並び・少ない並び

- **問い**: 同じ 12 枚の葉でも、並べ方で読む枚数が変わるか。
- **個人条件**: なし
- **URL**: A = 読む葉が最も少ない並び、B = 最も多い並び（`leaves=…`）
- **観察**: 読んだ葉の数、カットの数、根の値
- **考察**: 良い手を先に読むと刈りが増える理由（手の順序）。どちらでも根の値が同じ理由
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）

#### 課題 14. tic-tac-toe — MC が正しくなる試行回数

- **問い**: モンテカルロ法が完全解析と同じ手を選ぶには、何回試せばよいか。
- **個人条件**: シード = 30 + d（`preset=open-corner`。§10.2・§11 で変更）
- **URL**: A = 完全解と一致しない最大の N、B = 一致する最小の N（`mcn=…&mcseed=…`）
- **観察**: MC の推奨手、完全解の最善手、勝率の推定値
- **考察**: N を増やすと一致する理由。シードを変えると境目が変わる理由。完全解析と比べた長所・短所
- **教員の確認**: 教員用資料（公開リポジトリの外）に移した（§11）
