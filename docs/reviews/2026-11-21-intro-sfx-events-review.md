### INTRO-SFX-01（P1） 実装した新イベントを共有 URL で提出できない

- **問題**　提出課題は、新イベントの音を再現する URL A と、同じイベントの周波数だけを変えた URL B を求める。実装課題で合格したイベントはデモの発行ボタンや対象イベントに追加されず、ログでも観察できない。受け取った教員は、求められている比較を再現できない。
- **再現**　`algorithms/sfx-events.html?course=intro&ev=Hit&freq=880` を開く。初期の `soundFor` に `if (eventId === "Dash") return { freq: 730, dur: 0.09, gain: 0.12 };` を追加し、「動作テスト」を押す。「Dash に効果音を割り当てられました」と出る。提出欄 A で「今の設定を入れる」と、URL は `?ev=Hit&freq=880&dur=0.12&course=intro` になる。`?course=intro&ev=Dash&freq=730&dur=0.09&gain=0.12` を直接開くと、「ev=Dash は選択肢にないため無視しました」と表示され、選択は `Jump` になる。
- **原因**　提出欄は実装課題の入力を参照せず、デモのコントロールから共有 URL を作る。デモの発行・購読と選択肢は固定のイベント定義から作られる。実装課題は合否とメッセージだけを JSON に出すため、現在の JSON からも学生の関数を再検証できない。 [課題文](../../js/courses/intro-assignments.js#L210) · [URL 取り込み](../../js/platform/submission.js#L260) · [購読](../../js/sfx-events.js#L387) · [選択肢](../../js/sfx-events.js#L459) · [JSON](../../js/audio/topic-tasks.js#L50)
- **推奨修正**　既存イベントの A/B 比較は観察課題として提出し、新イベントは実装課題として、明示したイベント名と関数コードを提出できるようにする。教員が採用する提出物に合わせて、課題文・画面の手順・提出出力を揃える。
- **修正後の確認**　新規ブラウザセッションで A/B をそれぞれ開き、同じイベントの周波数だけが変わることを確認する。提出されたイベント名とコードから実装課題を再採点できることも確認する。既存の Hit 880 Hz、Jump 440 Hz、ミュート中の発行ログは回帰確認に使う。

### INTRO-SFX-02（P1） 新イベントの音を実装しなくても動作テストが合格する

- **問題**　初期コードの末尾にコメントで新しい名前を書くだけで、「音を割り当てられました」と表示される。すべてのイベントに同じ音を返す実装も合格するため、イベント名に応じて音を設計できるかを測れない。
- **再現**　初期コードのまま「動作テスト」を押すと不合格。末尾に `// "Dash"` だけを追加して再実行すると合格する。ブラウザと Node の両方で確認した。Node では、関数内に未使用の文字列 `"Dash"` があり、引数によらず同じ音を返すコードも合格した。また、未知の名前に `null` を返す正しい `Dash` の分岐があっても、その前に無関係な文字列 `"Note"` があると `Note` を採点し、不合格になる。
- **原因**　採点はソースから正規表現で最初の候補文字列を選び、その名前で返る数値の範囲を確認する。新イベント向けの戻り値と、未登録の名前に対する既定値を比較していない。 [採点ロジック](../../js/audio/audio-checks.js#L27)
- **推奨修正**　課題で使う新イベント名を入力欄などで明示させる。その名前を関数に渡して有効範囲の音が返ることを確認し、別の未登録名に対する戻り値との違いを検証する。未登録名に共通の音を返すか、無音を返すかは課題文で示す。
- **修正後の確認**　初期コード、コメントのみ、すべてのイベントに同じ値を返すコード、安全範囲を外れた値は不合格。既存 5 イベントを保ち、指定した新イベントの音を未登録時と区別した実装は、無関係な文字列の位置にかかわらず合格する。

### INTRO-SFX-03（P2） 2 種類の発行ボタンを使い分ける目的が伝わりにくい

- **問題と確認手順**　入門の「イベントと効果音」を開く。「ゲーム風イベント」と「直接 Emit」の両方に Hit がある。現行の演習手順は片方のボタンしか使わず、両方の Hit を押して何を比べるかを案内していない。
- **原因**　2 つの入口は同じイベントを発行する。見出しだけでは、一方がゲームの出来事を模した入力で、もう一方が購読側の動作を確かめるための入力だと読み取りにくい。 [デモの見出し](../../algorithms/sfx-events.html#L46) · [発行処理](../../js/sfx-events.js#L438) · [現行の演習手順](../../js/courses/intro-exercises.js#L161)
- **推奨修正**　各ボタン列のすぐ上に用途を 1 文で示し、入門の観察演習を下の順にする。周波数やログの答えは「期待される観察」に置き、予想と操作を先に読めるようにする。

#### 画面に載せる文案

| 場所 | 見出し | ボタン列やログの前に置く説明 |
|---|---|---|
| ゲーム風イベント | ゲームの出来事をまねる | Hit を押すと、キャラクターがダメージを受けたという知らせを送ります。 |
| 直接 Emit | イベント名を直接送る（Emit） | Hit などの名前を送って、受け取った側がどんな音を鳴らすか確かめます。 |
| ログ | ログ | `Emit` は送った知らせの名前です。`SE` には音を鳴らしたかどうかと、音の設定が出ます。新しい記録は上に出ます。 |

#### 観察演習の文案

**予想**　2 つの欄にある Hit を押すと、ログと音はどうなるでしょうか。

1. **押す場所だけを変える。** 「初期値に戻す」を押し、ミュートを解除します。「ゲームの出来事をまねる」の Hit と「イベント名を直接送る」の Hit を 1 回ずつ押します。新しく出た `Emit` と `SE` の行を見比べ、イベント名と周波数を記録します。
2. **音の設定だけを変える。** 「対象イベント」で Hit を選び、「周波数」だけを 880 Hz にします。両方の Hit をもう一度押し、ログのどの値が変わったかを確かめます。最後に Jump を押し、Jump の音の設定も変わったかを確かめます。
3. **ミュートで確かめる。** ミュートを入れて Hit を押します。新しい `Emit` の行が出るか、`SE` の行はどう変わるかを見ます。

**期待される観察**　はじめは両方とも `Emit Hit` と 120 Hz の再生が記録されます。周波数を変えると `Emit Hit` は同じで、両方の Hit が 880 Hz になります。Jump は 440 Hz です。ミュート中は `Emit Hit` と `SE (muted)` が出ます。

**確かめの問い**　Hit の音だけを高くしたとき、ゲームが送る知らせと、知らせを受け取った側の音の設定のうち、どちらを変えましたか。ログの行を一つ選び、理由を説明してください。

**発展**　「実験プレイ」の「ジャンプ」を押し、着地まで待ちます。「イベント名を直接送る」の Jump と Land を順に押したときと、ログのイベント名・周波数を比べます。実験プレイでは、着地した瞬間に Land が送られます。

**修正後の確認**　初期状態から文面どおりに進め、両方の Hit の再生が 120 Hz から 880 Hz に変わってもイベント名は同じこと、Jump が 440 Hz のままであることをログで比較できるか確認する。狭い画面でも各説明が対応するボタン列の近くで読めることを確認する。文案は提案段階で、表示と学習者による試行は未検証。

## 検証結果

- ローカルのブラウザで、演習リンクの条件に相当する Hit 880 Hz、Jump 440 Hz、ミュート中の `Emit Hit` と `SE (muted)` をログで確認した。初期コードの不合格、新イベントの分岐を追加したときの合格、コメントだけでの誤合格、共有 URL の生成と新イベント名を含む URL の読み込みも確認した。
- Node.js で、本番の `compileFns` と `TOPIC_TASKS["sfx-events"].run` を通して、初期コード、明示的な分岐、コメントのみ、全イベントで固定出力、範囲外、無関係な文字列が先にある場合の6件を確認した。範囲外の新イベントの音は不合格になった。
- `python3 scripts/smoke-platform.py` は、内部で動く Node のスモークテストも含めて全件通過した。
- 実音の聴取、JSON のダウンロード操作、LMS への提出、公開版は未検証。レビュー対象のソースコードに変更はない。

## 対応（2026-11-21 · Grok Build）

ブランチ `grok/sfx-events-review`。sfx-events は修正 9→10。成熟度コードは revised のまま。

### INTRO-SFX-01

提出 URL の A と B は、Jump、Land、Hit、Pickup、UI の同じイベントで、周波数だけを変える共有 URL にした。新しいイベント名と `soundFor` は、実装課題の入力、提出票、動作テストの JSON（`event` と `source`）に入る。デモの発行ボタンと選択肢は、既存の 5 イベントのまま。

確認: 新しいブラウザセッションで Hit 880 Hz の URL を A に入れ、周波数だけを 500 Hz にした URL を B に入れた。イベント名は Hit のまま、長さと音量は同じ。`ev=Dash` を開くと選択肢にないため無視され、選択は Jump。実装課題の「提出票へ入れる」で、入力した名前と関数が提出票に入った。

### INTRO-SFX-02

採点はソースの最初の文字列を使わない。入力したイベント名を `soundFor` に渡し、安全な範囲の音が返ることと、ソースに出てこない未登録の名前との戻り値の違いを見る。課題文では、未登録の名前には音を返さないか、別の音を返す、と示した。

確認: 初期コード、コメントのみ、すべてのイベントで同じ音、範囲外は不合格。無関係な文字列が先にあっても、指定した名前を未登録の名前と区別した実装は合格。Jump、Land、Hit、Pickup、UI は周波数・長さ・音量の数を返したまま。

### INTRO-SFX-03

「ゲームの出来事をまねる」と「イベント名を直接送る（Emit）」の直前に、用途の 1 文を置いた。ログの前に、`Emit` と `SE` の見方を置いた。入門の観察演習は、初期値から両方の Hit を押し、周波数だけを 880 Hz にして比べ、ミュートを見る順にした。期待される観察に 120 Hz、880 Hz、440 Hz、ミュートのログを残した。

確認: 「初期値に戻す」のあと、両方の Hit は `Emit Hit` と 120 Hz。対象イベントを Hit にして周波数を 880 Hz にすると、両方の Hit が 880 Hz になり、Jump は 440 Hz。ミュート中は `Emit Hit` と `SE (muted)`。1280 と 390 で、説明は各ボタン列の近くにあり、横にはみ出さない。
