# Git 運用と分業ワークフロー

最終更新: 2026-07-21

---

## 1. リポジトリの正

| 項目 | 方針 |
|------|------|
| 既定ブランチ | `main` |
| `main` の意味 | **いつでも Pages 公開してよい** 状態 |
| タグ | 教材の区切りで `vX.Y.Z`（例: v1.0.0） |
| リモート | GitHub（未設定なら `scripts/publish-github.sh` または手動） |

ローカルだけの作業でも、**意味のある単位でコミット**する。  
セッション引き継ぎは `HANDOFF.md`、方針の正本は `docs/`。

---

## 2. ブランチ命名

| 種類 | パターン | 例 |
|------|----------|-----|
| トピック新規 | `topic/<id>` | `topic/minimax` |
| トピック改善 | `fix/<id>-...` / `feat/<id>-...` | `feat/bfs-multi-goal` |
| 共通基盤 | `platform/<short>` | `platform/paint-module` |
| ドキュメントのみ | `docs/<short>` | `docs/catalog-game-tree` |

1 ブランチ = 1 目的。基盤リファクタとトピック新規を混ぜない。

### 2.1 merge 済みリモートブランチ（不要マーク）

クラウド環境などで作った作業ブランチが `main` に merge 済みでも、**すぐ削除せず残す**ことがある。  
その場合は `HANDOFF.md` の「リモートブランチ（不要マーク・削除しない）」表に記録する。

- **不要（保持）**: tip が `main` に包含済み。新規作業の起点にしない。削除はユーザー判断時のみ  
- 一覧の正は `HANDOFF.md`（エージェントはここを見て不要ブランチを作業先に選ばない）

## 3. コミットメッセージ（推奨）

```
feat(bfs): 複数ゴール G の配置に対応
fix(ds-viz): ツリーのはみ出しを修正
docs: ゲーム木カタログを追加
platform: ペイント共通化の第一歩
chore: .gitignore 更新
```

プレフィックス: `feat` / `fix` / `docs` / `platform` / `chore` / `refactor`

## 4. 分業ロール

| ロール | 責務 | 主な成果物 |
|--------|------|------------|
| **仕様** | 学習目標・操作・画面・成功条件を決める | `docs/topics/<id>/SPEC.md` |
| **実装（UI/可視化）** | HTML/CSS/キャンバス・ステップ再生 | `algorithms/` `js/` `css/` |
| **実装（アルゴリズム）** | 探索本体・正しさ・エッジケース | `js/<id>.js` |
| **C# サンプル** | 受講生向け核ロジック | `samples/*.cs` |
| **レビュー** | PLATFORM 準拠・教材として通じるか | PR コメント |

少人数では1人が複数ロールを兼ねてよい。**兼ねる場合も SPEC を先に書く**。

---

## 5. トピック実装フロー（標準）

```
① カタログ登録（ready: false）
      ↓
② SPEC 作成（templates/SPEC.md をコピー）
      ↓
③ SPEC レビュー（学習目標・操作が固まっているか）
      ↓
④ ブランチ topic/<id> で実装
      ↓
⑤ チェックリスト消化（templates/CHECKLIST.md）
      ↓
⑥ main へマージ → ready: true
      ↓
⑦ HANDOFF / CATALOG / README を更新（**成熟度**も CATALOG と `TOPICS.maturity` を揃える）
```

成熟度（一発 / 調整 / 安定）の定義: [topics/MATURITY.md](./topics/MATURITY.md)。  
改訂を入れたら `oneshot` → `revised`。授業据え置きなら `stable`。

### ⑤ の最低確認

- [ ] ローカル `http.server` でトップ → デモが開く  
- [ ] 再生・1ステップ・リセットが動く  
- [ ] モバイル幅でも操作が使える  
- [ ] `TOPICS` の `ready` / `category` / **`maturity`** と CATALOG・実ページが一致  
- [ ] PLATFORM の用語・レイアウトから大きく外れていない  
- [ ] ステータス・再生・乱数・木レイアウト等を **platform に寄せた**（コピペ増殖していない）  


---

## 6. 基盤変更フロー

共有モジュールを触るとき:

1. 影響デモをリストする（`ready: true` 全件が対象になりがち）  
2. 小さく分割してマージ（巨大 PR を避ける）  
3. `docs/PLATFORM.md` を更新  
4. 可能なら代表デモ（BFS + A* + DFS）を手で確認

## 7. ドキュメントの置き場

| 種類 | 場所 |
|------|------|
| **計画の正本**（構想・期分け） | `docs/interactive_game_programming_material_plan.docx`（策定 2026年7月） |
| 方針・ロードマップ（md 要約・進捗） | `docs/ROADMAP.md` |
| 共通仕様 | `docs/PLATFORM.md` |
| 本ファイル | `docs/WORKFLOW.md` |
| トピック一覧 | `docs/topics/CATALOG.md` |
| トピック仕様 | `docs/topics/<id>/SPEC.md` |
| セッション引き継ぎ | `HANDOFF.md`（作業メモ） |
| 利用者向け入口 | `README.md` |

SPEC はコードより先か、**遅くとも実装 PR と同じタイミング**で main に入れる。

## 8. GitHub Pages / リリース

```bash
./scripts/publish-github.sh [repo-name]
```

- Pages: `main` / root  
- Release: `RELEASE_NOTES_vX.Y.Z.md` を用意してタグとセット

## 9. やってはいけないこと

- `main` に動かないデモを `ready: true` で載せる  
- SPEC なしで大きなトピックを直 push  
- `git push --force` を共有ブランチに使う  
- 生成物・秘密情報・巨大バイナリを不用意にコミット

## 10. 共同体制（Grok × Claude）

2026-09-26 改訂。7月版は「Grok = 起点 / Fable5 = レビュー専任 / Sonnet5 = 実装」の3役固定だったが、
実態（Grok も main で実装・リリースしている、Claude 側はレビューと実装を一つのセッションで回している）に合わせて書き直した。

### 10.1 役割

| | Grok（手元の `~/Project`） | Claude（クラウドのセッション） | ユーザー |
|---|---|---|---|
| 作業場所 | `main` に直接コミット | `claude/...` 作業ブランチ → PR | PR のマージ判断 |
| 主な担当 | 企画・判断、課題文などの確定、**ブラウザでの実測と目視**、リリース（タグ・Release） | レビュー（指摘・計画書）、実装（難しいものは Sonnet5 に任せ、独立に検証する）、PR 作成 | 最終承認、両者の橋渡し |
| できないこと | — | 公開サイトをブラウザで開く、タグを push する | — |

- Claude 側では、レビューと実装を同じセッションで行ってよい。ただし**レビューの指摘（文書）と修正（コード）は別コミット**にし、PR 本文でどの指摘への対応かを書く。
- 実装を Sonnet5 に任せた場合も、Claude が自前の検証（独立実装との照合など）をしてからコミットする。

### 10.2 連絡はリポジトリで行う

| 何を | どこに |
|------|--------|
| 判断・決定 | 該当する計画書・レビュー文書の末尾に「決定事項（誰, 日付）」節を追記 |
| 進捗 | `HANDOFF.md` 冒頭に日付入りの段落を追加。**自分の段落だけを足し、相手の段落は消さない**。衝突したら両方残す |
| 作業中の宣言 | `HANDOFF.md` 冒頭に「作業中: <領域・ファイル>（担当, 日付）」。終わったら消す |

### 10.3 衝突を避ける（ファイルの持ち分）

1. **正本は `main`**。作業を始める前に必ず pull する（Claude は PR を出す前に `main` を取り込む）。
2. Claude の PR 本文には**変更ファイルの一覧**を必ず書く。その PR が開いている間、Grok はそのファイルを編集しない。
3. Grok が「作業中」と宣言した領域は、Claude が避ける。
4. PR がマージされたら、Claude は作業ブランチを `main` に揃え直す（マージ済みの履歴に新しい作業を積まない）。

### 10.4 検証の分担

- **Claude**: コードでの検証（独立実装との照合、`python3 scripts/smoke-platform.py`）と、**ローカルのブラウザでの値の実測**。
  リポジトリを `python3 -m http.server` で配信し、ヘッドレスの Chromium（Playwright）でページを操作して、画面に出る数値・DOM・コンソールエラーを確かめられる。
  公開サイトには接続できない。見た目の良し悪しや、人の手の操作に依存する挙動は判断できない。
- **Grok**: ブラウザでの目視と手操作（レイアウト・色・操作感・モバイル幅、キー操作のタイミングに依存する挙動）と、公開サイトでの確認。
- 両方そろって「確認済み」とする。片方しか済んでいないときは、HANDOFF にどちらが未確認かを書く。

### 10.5 共通の決まり

1. 成熟度の3か所（`docs/topics/CATALOG.md`・`js/platform/maturity.js` の `TOPIC_META`・`js/main.js` の `TOPICS`）は、変更した側が同じコミットで揃える。
2. smoke テストの通過は必須。
3. リリース番号は Grok が決める。Claude はリリースノートの草案までを担当する。
4. 方針が分かれるもの（選択肢が複数あり優劣が明確でないもの）は、どちらも決め切らずにユーザーに確認する。
5. 正本 docx の書き換えはユーザーの承認が前提。

### 10.6 典型的な流れ

1. Claude がレビューし、指摘と改善計画を `docs/reviews/` に置く（PR → マージ）
2. Grok が「決定事項」を追記し、ブラウザで期待値を実測して確定する
3. Claude が実装して PR を出す（変更ファイル一覧つき）
4. ユーザーがマージを判断する
5. Grok が pull してブラウザで目視確認し、問題がなければリリースする。問題があれば HANDOFF に書く
